# Project instructions
Read the design before implementation. The user wants beautiful actual 2D pixel art, fast mobile controls, satisfying attack/defence, and operators with mechanical identity. Never substitute a 3D/isometric scene or generic grenade abilities.

Inspect existing repo instructions, engine, dependencies, assets, and working gameplay first. Preserve working features; explain material changes. If this is a new repo, proposed stack is TypeScript, Phaser, and Vite. Verify current compatible official documentation at implementation time, pin versions, commit the lockfile. No paid services or API keys are necessary. Do not silently deploy, buy assets, or enable online multiplayer.

Build in milestone order. Keep a PROGRESS.md with completed work, current build/run commands, evidence, gaps, and next steps. Separate simulation from presentation; stable IDs for content; no God file. Every signature gadget needs its own visible lifecycle, touch affordance, enemy reaction, counterplay, cancellation, and test. Do not simulate a gadget by changing a stat while the character throws the same generic projectile.

Use authored, coherent licensed or original sprites. Temporary geometry is allowed during mechanics work but label it. Never call a prototype polished without active gameplay review. Do not use ripped Siege/PUBG characters, icons, audio, logos, or maps.

Full multiplayer, vertical floors, prone/lean controls, realistic demolition, live-service monetisation, and extra modes are out of the initial scope. No weakening fair perception to make bots appear competent. No permanent combat-stat progression.

At the first playable slice and polish milestone, report controls, launch steps, actual gameplay evidence, and known gaps; request focused feedback before large expansion. Complete authorized work up to that review point. Never claim real iPhone tests from desktop emulation. Implement missing behaviour rather than making tests ignore it.
